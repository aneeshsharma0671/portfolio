# PWA Caching Implementation Plan

## Goal
Cache the Sudoku game assets so it works offline, and always loads the latest version when online.

## Strategy: Stale-While-Revalidate
- First load: fetch from network, cache everything
- Subsequent loads (online): serve from cache instantly, fetch fresh in background
- Offline: serve from cache silently

## Website Changes (portfolio repo)

### 1. Install next-pwa
```
npm install next-pwa
```


### 2. Update next.config.js
Wrap config with `withPWA`, scope service worker to `/games/sudoku` only:
```js
const withPWA = require('next-pwa')({
  dest: 'public',
  scope: '/games/sudoku',
  sw: 'sw-sudoku.js',
  register: false,        // we manually register so scope is correct
  skipWaiting: true,
  disable: process.env.NODE_ENV === 'development',
})
```

### 3. Register service worker manually in SudokuGame.tsx
```ts
useEffect(() => {
  if ('serviceWorker' in navigator) {
    navigator.serviceWorker.register('/sw-sudoku.js', {
      scope: '/games/sudoku',
    })
  }
}, [])
```

### 4. Precache assets
next-pwa auto-generates the precache manifest on build — all JS/CSS chunks
for the `/games/sudoku` route get cached on first load.

### 5. Runtime caching rules (in next.config.js)
```js
runtimeCaching: [
  {
    urlPattern: /^https:\/\/thesharmaproject\.com\/games\/sudoku/,
    handler: 'StaleWhileRevalidate',
    options: {
      cacheName: 'sudoku-game',
    },
  },
  {
    urlPattern: /^https:\/\/fonts\.googleapis\.com/,
    handler: 'CacheFirst',
    options: {
      cacheName: 'google-fonts',
      expiration: { maxAgeSeconds: 60 * 60 * 24 * 365 },
    },
  },
]
```

## App Changes (Sudoku-plain repo)

### None required
WebView uses the service worker automatically since it's part of the page.
The Android app just loads the URL as before.

## Testing

### Online
1. Load app → game loads fresh
2. Check DevTools → service worker registered, assets cached

### Offline
1. Load app once online
2. Disable network (adb shell svc wifi disable && adb shell svc data disable)
3. Reload app → game loads from cache

### Update flow
1. Deploy new version to website
2. User opens app online → stale cache served instantly
3. Service worker fetches new assets in background
4. Next time user opens app → new version served from updated cache

## Notes
- Service worker scope is strictly `/games/sudoku` — no other pages affected
- Future games get their own service worker: `sw-chess.js`, `sw-wordle.js` etc.
- `skipWaiting: true` ensures new service worker activates immediately on next load
- Disable in development to avoid stale cache during dev
